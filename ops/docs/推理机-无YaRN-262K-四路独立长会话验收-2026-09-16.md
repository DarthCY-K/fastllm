# 无 YaRN 原生 262K × 4 独立长会话容量验收（2026-09-16）

## 目的

验证 4×2080 Ti TP4 的当前 NVFP4 W4A16 + DFlash2 引擎，在关闭 YaRN 后是否能以原生 262,144-token 单会话上限，复用 1M 全局 Paged KV 池，同时执行四条**不同前缀**的长会话。

这不是“同前缀 fan-out”测试：四路输入在开头即带不同 `LOAD_CASE_xx_UNIQUE_PREFIX`，服务端四路均报告 `cached_tokens=0`。

## 候选参数

```text
--max_context_length 262144
--tokens 1048576
--max_batch 4
# 无 --rope_scaling
--kv_cache_dtype fp8_e4m3
--chunked_prefill_size 512
--tp 0,1,2,3
--speculative_algorithm dflash
--speculative_num_draft_tokens 8
```

启动日志实证：

```text
Model context window: 262144 tokens per session
model=262144, shared KV cache=1048576, configured limit=262144
KV Cache Token limit: 1048576 tokens (8192 pages × 128)
Batch limit: 4
Fastllm Scheduler: Qwen3.5 MTP (lane=4)
```

## 工作负载

- 4 路 `ThreadPoolExecutor` + Barrier 同时提交
- 每路不同前缀；实际 `prompt_tokens=199,960`，全部 `cached_tokens=0`
- 每路 `max_tokens=min_tokens=32,768`，`temperature=0`，关闭 thinking
- `min_tokens` 通过 OpenAI Chat Completions 映射到 FastLLM 的 `output_token_least`，避免模型自然 EOS 提前结束

每路总计：`199,960 + 32,768 = 232,728` token。
四路总计：`930,912` token，低于 1,048,576-token 全局 KV 池，余量 `117,664` token。

## 时延分解

四路冷预填仍串行：日志共有 4 个 `Long Prefill ... (512/199960)` 起点和 4 个完成点。

- 4×32,768 = 131,072 输出 token
- 按实测约 328 tok/s 聚合 decode，decode 约 399.6s（6.66min）
- 剩余约 1,059.5s（17.66min）是四路独立冷 200K prefill 的排队/预填

因此 24 分钟不是“batch4 decode 很慢”；批量 decode 已确认真实 `alive=4`。冷态多长文的首字排队仍是此方案的主要限制。

## 结论与边界

1. **容量成立**：无 YaRN 262K + 保留 1M 全局 KV + batch4，可稳定承载 4 条独立约 200K 输入 + 32K 输出会话。
2. **历史 262K 档不是并发档**：它同时设了 `--tokens 262144`，全局 KV 只有 262K，因此只能单路；不要与本验收混为一谈。
3. **262K 输入满额 × 4 不实用**：4×262,144 恰好耗尽全局池，零输出余量。应为输出、DFlash 草稿和系统开销保留页。
4. **本验收是容量/调度/稳定性验收**：输出为确定性计数负载，未替代 Agent 质量、多工具回环、图片、或混合长度的语义验收。
