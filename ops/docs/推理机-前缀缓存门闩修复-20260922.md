# 推理机 ·「重复长问题偶尔卡 5–10 秒」修复报告（2026-09-22）

## 一句话结论
**修好了，已上线生产。** 同一个长问题重复问时，本该"秒回"却偶尔干等 5–10 秒的问题，
根因是引擎的硬盘缓存"清仓"动作太慢、期间独占盘锁，所有来读缓存的请求只能排队。
修复后清仓持锁降到 **0.55–0.78 秒**（生产口径），暖请求实测 **0 次卡顿**（修复前同探针抓到 2 次、最长 3.1 秒；更早的复现最长 5.4 秒）。可一键回滚。

## 1. 现象与影响（人话）
- **现象**：把一篇几万字的材料丢给模型，第二次再问同样内容，本该立刻复用缓存"秒回"，
  但偶尔会先愣 5–10 秒才开始出字；愣着的时候 4 张显卡全闲着（GPU 0%、功耗空转），
  之后就恢复正常。
- **影响**：偶发的"半天没反应"，体感像卡死；重复长问题的场景（长文反复改问）最容易撞上。
- **不是**显卡、不是盘慢、不是网络：这期间显卡空闲、盘也没在干活，是引擎内部自己把路堵住了。

## 2. 根因（一句话 + 证据链）
**一句话**：引擎每次要往硬盘缓存里存新东西之前，得先"清仓"腾地方；
原来的清仓是**一边删一边逐笔记账**，而数据库开了"每笔必落盘"模式（synchronous=FULL），
**每笔记账都要等一次硬盘确认（实测 1.1ms）**，一轮清仓要记几千笔 → 2–3 秒起步；
这期间它独占缓存目录的"总钥匙"（.lease 排他锁），谁来读缓存都得排队干等。

**证据链（全部本机实测，非推测）**：
1. 复现停摆窗内抓锁：`.lease` 与 `.metadata` 排他锁被引擎线程持有 ~5 秒，释放时刻与请求恢复对齐。
2. 停摆窗内 `intents=0`（没有写者在用锁）→ 指向唯一的**维护动作**（`Maintain()`/清仓），
   源码核实：运行期只有它拿 `.lease` 排他锁（另一处是启动构造函数）。
3. 微基准（不停机实测本机盘）：单个文件 fsync ≈ **1.1ms**、目录 fsync ≈ 0、WAL checkpoint ≈ 0.1ms
   → "fsync 本身慢"被排除；但**逐笔删除 = 每笔一次 fsync**。
4. 引擎内计时打印（本次新增）：一轮清仓要删 **1424–2590 个对象**（1.1–1.9GB），
   在旧实现下 ≈ 1500–2800 次 fsync ≈ **2–3 秒** —— 与观测到的锁持有 1.8–3.1 秒严丝合缝。
5. 反面排除：Recover（重建索引）路径本轮未触发（日志无对应打印）、写者未参与（intents=0）、
   盘本身残读 5.4GB/s 远远没跑满。

## 3. 第一版为什么没修好（诚实记录）
v1 的假设是"每次清仓都做了多余的收尾动作（目录同步、WAL 重写）"。同窗 A/B 实测两臂**完全一样**
（暖波同样卡 2.7–2.8s、锁同样 1.8–3.1s）→ 证明那些收尾动作本来就只有毫秒级，
**真正的大头（逐笔记账的 fsync 等待）当时没动**。修正假设后才有 v2。

## 4. 最终改法（v2，源码 src/utils/disk_prefix_cache.cpp）
1. **清仓整段并入一个事务**：几千笔删除只在最后等一次硬盘确认（实测收尾 ≤5ms）；
2. 孤儿对象清理：从"每轮全表扫描"改为**按引用精确回收**；
3. 读路径（列清单）不再拿排他小锁，改无锁快照读（写侧安全校验保留）；
4. 新增引擎内计时打印：`[Prefix SSD] gc: evicted=… objects=… freed=…MB held=…ms (txn=…ms tail=…ms)`。
