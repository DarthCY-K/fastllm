# 推理机 FastLLM · 视觉×前缀复原静默跳过修复（2026-09-17）

## 症状与复现（2026-09-16 夜 ~ 17 晨）

- 生产症状：客户端（Hermes/Pi）发出**新图片**后，模型对着图片占位符**自信编造**内容，引擎日志无任何 `[Vision]` 行；请求耗时仅数百 ms（"快而错"）。
- 8+ 对照收窄：凡是请求命中前缀复原（`prefix cache restored: tokens=N>0`）时，**位于复原边界之后的增量区图片不做视觉编码**；冷算（无复原）100% 正常。
- 影响面：任何「已有前缀 + 新图」场景（连续发不同图、多模态评测、Hermes 图片会话）；图在复原区内的同图自续/文本续问不受影响（mmcache、pool-trim 的验收均落在该类，故此前未暴露）。

## 根因（源码级）

- `src/models/qwen3_5.cpp`：`Qwen35ForwardMultimodalInternal` 的复原分支（`pastKeyValues` 非空，33443 起）**直接走普通 `Forward`/`Qwen35MTPForward` 后 return**，完全绕过 `EncodeVisualItems` / `BuildMultimodalPositionData`（两处调用点 33503/33512 均在冷算路径）。
- 增量区新图的占位 token 以纯文本 embedding 前向 → 模型"看不见"图，仅凭上下文词语编造描述。

## 修复（v1 保护：跳过复原，正确优先）

- 位置：`Qwen35MTPLoop` 内 `tryRestorePrefixCache` —— `cachedLen` 最终确定后、执行破坏性复原（`RestorePagedPrefixCacheExtra`）前，扫描增量区 `[cachedLen, size)` 是否含图像/视频占位 token（`image_token_id`/`video_token_id`）。
- 命中 → 打印 `[Qwen3.5 MM] prefix restore skipped: media tokens in delta (restore_len=…, total=…)` 并 `return 0`（放弃复原 → 全量冷预填，走已验证的冷算视觉路径）。
- 开关：`FT_QWEN35_MM_RESTORE_GUARD`（默认开；=0 关闭保护，manager env 即可，无需改代码）。
- 语义：**仅当增量区不含媒体占位 token 时才复原**；文本增量、图在复原区内的续问/重发完全不受影响。
- 补丁：`ops/deploy/apply_mm_restore_guard.py`（幂等，+45 行，单文件 qwen3_5.cpp；备份 `*.bak-pre-mmguard`）。

## 遗留与后续

1. **v2 方向（性能）**：复原分支内为增量图补 `EncodeVisualItems` + delta mm 位置数据合流（只编码未被复原 KV 覆盖的图），可把「含新图请求」从全量冷预填拉回增量预填。本次 v1 以正确性优先：含新图请求的代价是**全量冷预填**（与修复前的"快而错"相比只慢不错）；是否做 v2 视客户端实际带图频率评估。
2. P3/P7 的 OCR 细节（G→C）：模型对 76px DejaVu 粗体的偶发混淆，冷算路径同样存在，与复原逻辑无关。
3. 「复原边界切在旧图内部」的情形由本保护一并覆盖（增量区含旧图尾部 pad 时同样跳过复原 → 冷算），无需额外分支。
