# 推理机 big 池请求结束回收 — 修复记录（2026-09-16）

## 结论

**根因**：长会话多模态负载下，Qwen3.5 多模态/DFlash 路径按“本次 token 数”分配大小多变
的大临时块（视觉编码 `EncodeVisualItems/PrepareVision`、`AppendDFlashTargetHidden`、
`EnsureDFlashRotary`、worker `ForwardSingleGPU→CopyFrom`、长预填 100–588MB 块）。
这些块用完后退回 CUDA big 池成为**空闲块，但既不重用（尺寸不断变化）也不回退设备**
（池只在 OOM 重试时释放），device0 显存单调增长（实测 +5.6GB/20min），直到某次中等分配
失败 → `AllReduce rendezvous 超时` → SIGABRT → systemd 重启。15:10 与 19:07 两次崩溃同源。

**修复**：请求结束时释放 big 池中 ≥1MB 的空闲大块（busy / graphPins / 图保护块保留），
让 device0 在请求间回到基线；小块热池保留复用。

## 代码改动

1. `src/devices/cuda/fastllm-cuda.cu`
   - `FastllmCudaTrimIdleBigBuffers(size_t minBytes)`：释放各设备 big 池中 ≥minBytes 的空闲块
     （保留 busy / graphPins>0 / `FastllmCudaGraphPoolPointerProtectedLocked`），打印
     `[Fastllm] idle big-buffer trim: released N block(s), X MB`。
   - `FastllmCudaRequestEndPoolTrim()`：统一入口，env 门控
     （`FT_QWEN35_REQUEST_POOL_TRIM` 默认开、`=0` 关闭；`FT_QWEN35_REQUEST_POOL_TRIM_MIN_MB` 默认 1）。
2. `include/devices/cuda/fastllm-cuda.cuh`：两函数声明。
3. `src/models/qwen3_5.cpp`：`Qwen35MTPLoop` 中 isEnding 清理处 + abort 清理处调用统一入口。
4. `src/models/basellm.cpp`：`basellm::RemoveResponseContext` 末尾调用统一入口
   —— 覆盖所有请求完成路径（不限 MTP/多模态）。

## 遗留与后续

- 每请求重回收的延迟代价：实测 ≤0.2s 级（64K 冷预填 66.6→64.3s，未见劣化）；若后续要省，
  可用 `FT_QWEN35_REQUEST_POOL_TRIM_MIN_MB` 调阈值（如 8/16）折中。
- 视觉路径每请求重编码（10–15MB×N）+ 历史图片导致前缀缓存全量失配（`in=88.6K, cr=0`）
  仍是效率问题，另项处理；客户端可配合 `pi-image-prune` 清理历史图。
- 追踪件（FT_CUDA_ALLOC_TRACE）建议 soak 观察 1–2 天，确认无爬升后在生产 unset。
- 修补丁应同步到 GitHub fork（`DarthCY-K/fastllm` 分支 `sm75-2080Ti`），按既有 bundle 推送路径。
