# 推理机 SSD 前缀缓存 —— 启动恢复惰性化（lazy-recover）2026-09-21 夜

## 背景（v1 问题）
每次引擎进程启动（切换/重启/崩溃/掉电）后的**首个请求**承担"全量恢复"：扫描并解析全部 commit 文件、逐 ref 校验、重建 SQLite 索引（每实例一次，Ensure 下有两个存储实例）。成本随 commit 元数据量线性增长，实测 28G 存量时约 95s；且系统层无自动暖机时，这笔开销直接暴露给第一个真实请求。

## 改造内容（分支 `lazy-recover-20260921` @ `wt-lazy`，基线 r11 = 5f6c1961）
1. **`IndexUsable()` 快路径**：ctor 不再无条件全量恢复；先验证既有索引可用（DB quick_check + objects/checkpoints/refs 三表存在 + intents 为空）。可用 → 直接跳过（日志 `[Prefix SSD] index ok: fast startup, full recovery skipped.`，写 `recover-progress.json {phase: fast-skip}`）。
2. **需重建时才重建**：索引缺失/损坏/intents 残留（中断写）→ 走原全量恢复；可显式强制：`FASTLLM_PREFIX_CACHE_FORCE_RECOVER=1`。
3. **`Maintain()` 同样先 `IndexUsable()`**：配额淘汰维护不再每次都重建索引（干净时跳过），崩溃残留时照旧重建清障。
4. **全量恢复进度遥测**：恢复过程中每 4 个 commit 写 `v2/recover-progress.json`（commits_done/commits_total/refs_checked/objects_removed/started_ns/updated_ns/detail）+ 起止日志行（`full recovery starting: commits=N` / `done: commits=N refs=N objects_removed=N elapsed=Xs`）。供 `warmup_status.py` 查询。
5. **正确性依据（为何可以信任既有索引）**：
   - DB 只做**候选选择**；真正的恢复是**按需校验**——`LoadRecord` 重读 commit 文件 + Digest 校验、逐 ref `HeaderValid`、`ReadBytes` 逐块 sha256。DB 过期/失配只会退化为 miss，不会错读数据。
   - 中断写残留（intents 非空）→ 自动全量重建；upstream 单测覆盖 SIGKILL/索引损坏场景。
   - 快路径不执行 transport 清扫（孤儿 blob 由下次全量恢复或 Maintain 的对象 GC 回收）；不新增删除路径。

## CPU 级验收（build-lazy；测试副本 = 生产 store 硬链接拷贝，16G / 17391 文件 / 29 commits / 74,914 refs）
| 场景 | 结果 |
|---|---|
| T1 干净索引（快路径） | **ctor 56.7ms**，checkpoints=29（与全量一致），progress=fast-skip |
| T2 FORCE_RECOVER（全量恢复） | **17.57s**（29 commits / 74,914 refs，objects_removed=0），progress=done 完整 |
| T3 脏索引（intents=1 → 自动重建） | **17.6s**，intents_after=0，checkpoints=29 |
| T4 upstream 单测全套（含跨重启/SIGKILL/损坏/FIFO） | **PASS** |

原始输出见 `ops/evidence/lazy-recover-20260921/matrix.txt`。

## 说明与回退
- 本分支**未上生产**；无 .so 转正则对产线零影响。
- 全量恢复成本为 commit 元数据的线性函数（本店实测 ≈0.6s/commit；引擎侧两实例理论 ≈2×）。
- 回退：不用该分支即可；如转正后需回退，用 r11 的 overlay。
- 待办（窗口）：引擎级 e2e —— 首请求耗时观测（期望秒级）+ 跨重启恢复 md5 复验 + auto-warmup/状态查询联动。
