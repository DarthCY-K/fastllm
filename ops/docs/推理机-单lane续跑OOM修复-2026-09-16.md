# 推理机：单 lane 长续跑 OOM 修复（2026-09-16）

## 现象

Pi 的 Minecraft 会话在工具读取 `game.js` 后，将约 24,000 字符工具输出带入下一轮。该轮客户端用量为：

- 新输入 `20,436` token
- 前缀缓存命中 `15,872` token

服务端在 GPU0 上出现：

```text
Error: CUDA error when allocating 363 MB memory on device 0!
gpuFree: 147 MB / 22009 MB
Error: AllReduce host submission rendezvous timed out
terminate called after throwing an instance of 'char const*'
```

随后 `fastllm-qwen38-tp4.service` 因 `Restart=on-failure` 自动重启。

## 根因

生产参数为 `--max_batch=1`，启动日志为：

```text
Fastllm Scheduler: Qwen3.5 MTP (lane=1).
```

`Qwen3_5Model::scheduledDecodeTokens()` 旧逻辑仅在 `useMtpBatchScheduling`（lane > 1）时，才将已预填会话（`preTokens > 0`）的多 token 续跑限制为 DFlash 一步的 token 数。

因此 lane=1 时，10,285-token 的续跑被当作一次 `Qwen35MTPForward` 的 decode forward。日志对应：

```text
[NVFP4 prefill cuBLAS] GPU 0: active, rows=10285 N=4096 K=5120
```

该路径绕过常规 `chunked_prefill_size=512` 的长期预填保护，在 GPU0 基线显存与 DFlash/TP 临时张量之上产生大分配，最终 363 MiB 分配失败。AllReduce 超时是 OOM 后某个 rank 退出集合通信的次生症状，不是首因。

## 修复

所有 `preTokens > 0` 的多 token 续跑都限制到 `mtpBatchDecodeTokens`：DFlash2 当前为 8（7 draft + 1 target），不再依赖 scheduler lane 数。

```cpp
if (ctx->preTokens > 0 && tokens > 1) {
    tokens = std::min(tokens, mtpBatchDecodeTokens);
}
```

这会把超长工具结果分多步消化。代价是该异常续跑不再按一次大 prefill 完成；收益是峰值临时张量受单步上限约束，不会耗尽 GPU0。

1. `test/regression/test_qwen35_single_lane_continuation_chunk.py`
   - 修复前 RED：lane=1 返回 10,285，而不是 8。
   - 修复后 GREEN：单 lane、多 lane 均 clamp；新 prompt 与单 token decode 不变。
2. 候选 `.so` 构建：`06dc99415c9bddf2dd4579bd7c7500f1`。
3. 生产切换：原 `de41af83cefee14cd829bd63dec40ecd` 备份为：
   `/home/ai-agent/builds/fastllm-video-venv/lib/python3.13/site-packages/ftllm/libfastllm_tools.so.wheelbak-20260916-pre-contclamp`
4. 服务回线：34s；认证梯（401/401/200）、非流式和流式（含 `[DONE]`）均通过。
5. 长负载验收：65,625 prompt token，68.67s，精确返回 `LONG_CLAMP_OK`；四卡采样峰值为 `16162/14788/14788/14768 MiB`；`NRestarts=0`，错误窗口无 CUDA OOM / AllReduce timeout。

外部 Chat Completions API无法直接构造一个已有内部 `ResponseContext` 的续跑状态，因此生产长负载验证覆盖内存边界与服务可用性；分支本身由先红后绿的 scheduler regression test 覆盖。
