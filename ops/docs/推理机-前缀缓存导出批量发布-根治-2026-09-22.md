# 前缀缓存「导出批量发布」修复（2026-09-22）

## 症状
后台把 KV 快照导出到 SSD 前缀缓存，单趟 8K 快照耗时 ~6.0s（即便这趟只新增 82KB 内容），
32K 题四个提交阶梯间隔 6.15 / 6.53 / 6.79s。该窗口内重复问同一题会走冷路径（本该秒回）。
日常几乎无感，但属于「本该秒回却要多等」的确定性浪费，且随负载线性放大。

## 归因：零窗口线程采样（thr_probe.py，只读，不注入）
对生产引擎进程每 5ms 采样各线程 syscall / wchan / CPU，导出窗口内导出线程分布：

| 状态 | 占比 | 明细 |
|---|---|---|
| fsync/fdatasync 等日志提交 | ~71% | `jbd2_log_wait_commit` 56+33、`submit_bio_wait` 38、`folio_wait_bit_common` 4 |
| 连接器 poll | ~8% | `do_sys_poll` 15 |
| 用户态（哈希/拷贝） | ~18% | 33 |

即瓶颈 = **每个分片 4 次同步落盘确认**（各自一次 jbd2 日志提交，~8ms/次）：
1. intent INSERT（独立事务）
2. 暂存文件 fsync（SyncFile）
3. objects/consume/intent-delete 合并事务提交
4. 暂存目录 SyncDirectory

128 分片 × ~35-45ms ≈ 5s+，与实测 6.0s 吻合。
**与 GC 门闩同宗：synchronous=FULL 下的提交次数过多**（彼时是"一行 DELETE 一次 fsync"，
此处是"一片数据四次确认"）。
反证：8MB 分片盘侧微基准「写+fsync+改名+目录同步」仅 13ms、去重命中 6.5ms → 单盘本身不慢。

## 修法（src/utils/disk_prefix_cache.cpp，lib-only，不动引擎调用面）
`WriteSession::State` 新增 `pending` 组与 `FlushPending()`：
- **StoreBytes**：暂存写完后只入 pending（删掉逐分片 intent / rename / 目录同步 / 事务）；
  同一 session 内去重仍按 hash 走 `verified` 表。
- **FlushPending**：每 16 片或 64MB（或 Commit 前）触发一次——
  一条 batch 粒度 intent → 逐片 SyncFile（**首条 fsync 的日志提交顺带 flush 整批脏页，
  后续 fsync 秒回**）→ `BEGIN IMMEDIATE` 单事务内逐片 rename + objects 登记 + consume
  → 提交 → 一次目录同步。
- **Commit**：先 `FlushPending()`，保证清单永不引用未落盘数据。
- 崩溃语义（与既有设计一致）：暂存数据先落盘、再改名、再登记；
  崩在批中只会留下「无登记 blob」，由 GC 孤儿清扫回收，**不会发布坏清单**；
  `.metadata` 排他锁 + 单事务保证批内原子。
